# História 05 — MockTransport

**ID:** 0008  
**Área:** ECU Communication Layer  
**Fase:** 2

---

## Contexto

O `EcuConnectionMock` atual replica um CSV com timing baseado em timestamps, mas não simula o protocolo request/reply da ECU. Como a `EcuSession` vai fazer um handshake síncrono (`#D50`, `#I20`, `#I21`, `#F01`..`#F16`, `#D01`), o mock precisa responder corretamente a esses comandos, caso contrário o handshake ficará bloqueado aguardando respostas que nunca chegam.

O `MockTransport` implementa `EcuTransport` e substitui `EcuConnectionMock`, acrescentando a simulação do protocolo de handshake.

---

## História de Usuário

Como desenvolvedor, quero um `MockTransport` que replaya um CSV de log e também simula as respostas de handshake da ECU, para que o modo mock seja funcionalmente equivalente ao modo serial durante o desenvolvimento e testes.

---

## Requisitos Funcionais

- `MockTransport` implementa `EcuTransport`.
- Durante o handshake (antes do streaming iniciar), `write()` interpreta o comando e enfileira a resposta apropriada:
  - `#D50` → enfileira `#D50;OK\n` (ou string fixa de info da ECU)
  - `#I20` → enfileira `#I20;<16 valores de RPM separados por ;>\n`
  - `#I21` → enfileira `#I21;<16 valores de MAP separados por ;>\n`
  - `#F01`..`#F16` → enfileira `#Fxx;<16 valores de VE da linha xx>\n`
  - `#D01` (streaming start) → enfileira `#D01;OK\n` e inicia replay do CSV
- Após o streaming iniciar, `readline()` retorna linhas do CSV em ordem, com timing aproximado baseado nos timestamps (comportamento atual do `mock_log.py`).
- `write()` para comandos fire-and-forget (`#D04`, `#D05`, `#D06`) pode ser no-op.
- `connect()` carrega o CSV em memória. `disconnect()` para o replay.
- `is_connected()` retorna `True` após `connect()`.

---

## Requisitos Não-Funcionais

- Valores hardcoded para breakpoints e VE no handshake são aceitáveis se o CSV não contiver esses dados.
- O replay deve simular o timing sem `time.sleep()` bloqueante — usar diferença de timestamps do CSV para calcular quanto aguardar.
- Thread safety: `write()` pode ser chamado de thread diferente de `readline()`; usar `queue.Queue` para comunicação.

---

## Especificação Técnica

### Estrutura interna do MockTransport

```
_response_queue: queue.Queue   # respostas de handshake enfileiradas pelo write()
_csv_lines: list[tuple[float, str]]  # (timestamp, linha) carregadas do CSV
_streaming: bool               # True após receber #D01 (start streaming)
_start_time: float             # time.time() quando streaming iniciou
_csv_start_ts: float           # timestamp da primeira linha do CSV
```

### `readline()` — lógica:

```
se não streaming:
    retornar _response_queue.get(timeout=3.0)  # bloqueia aguardando resposta de handshake
se streaming:
    pegar próxima linha do CSV
    calcular delta de tempo relativo ao início do replay
    sleep até o momento correto
    retornar linha
    se CSV esgotado: reiniciar do início (loop) ou retornar ""
```

### Formato do CSV de replay

O CSV existente em `app/ecu_connection/mock_log.py` tem colunas: `Timestamp; Event; #D01 campos...`. A primeira linha de dados `#D01` contém os valores do frame D01. O MockTransport deve emitir essas linhas como `#D01;v1;v2;...` reconstituindo o formato do protocolo.

> **Nota:** Se o CSV não contiver dados de D02, o MockTransport pode emitir apenas frames D01. O LogWriter aguarda D01+D02, mas o SignalProcessor funciona com dados parciais.

### Valores padrão para handshake (hardcoded no MockTransport):

```python
_DEFAULT_RPM_BREAKPOINTS = [500, 1000, 1500, 2000, 2500, 3000, 3500, 4000,
                             4500, 5000, 5500, 6000, 6500, 7000, 7500, 8000]
_DEFAULT_MAP_BREAKPOINTS = [20, 40, 60, 80, 100, 110, 120, 130,
                             140, 150, 155, 160, 165, 170, 180, 200]
_DEFAULT_VE_ROW = [800] * 16   # 80.0% para todas as células
```
