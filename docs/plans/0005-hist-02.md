# HIST-02: Criar EcuSession — Camada de Protocolo com Threading Internalizada

## Contexto

Atualmente `EcuConnectionSerial` e `EcuConnectionThread` juntos formam uma camada que mistura protocolo, handshake, retry e gerenciamento de thread. A `EcuConnectionThread` é instanciada em `app/ecu_connection/__init__.py` e iniciada em `main.py`, tornando a thread visível externamente. O objetivo é criar uma `EcuSession` que internalize as threads, implemente o protocolo de request/response e exponha métodos de negócio nomeados.

## História de Usuário

Como desenvolvedor do projeto, quero uma `EcuSession` que gerencie internamente suas próprias threads de leitura e escrita, implemente o handshake de conexão e o protocolo de request/response, e exponha métodos nomeados como `open_loop()` e `close_loop()`, para que o `main.py` não precise gerenciar threads de ECU.

## Requisitos Funcionais

- RF01: `EcuSession` aceita um `EcuTransport` no construtor.
- RF02: `EcuSession.start()` inicia duas threads internas: uma de leitura (`_read_loop`) e uma de escrita (`_write_loop`), ambas `threading.Thread` (não `QThread`).
- RF03: `EcuSession.stop()` para ambas as threads e fecha o transport.
- RF04: A thread de leitura executa o handshake de conexão na inicialização: `_start_communication()` → `_fetch_breakpoints()` → `_fetch_ve_map()` → `_start_streaming()`. Após o handshake, entra no loop de streaming.
- RF05: Durante streaming, cada linha lida é classificada:
  - Começa com `#D01` → publicar `EcuMessFrameEvent(frame_id="D01", raw_line=line)` no EventBus.
  - Começa com `#D02` → publicar `EcuMessFrameEvent(frame_id="D02", raw_line=line)`.
  - Começa com `#D03` → publicar `EcuMessFrameEvent(frame_id="D03", raw_line=line)`.
  - Qualquer outra linha → verificar se é resposta esperada de um comando pendente (roteamento interno via `_response_queue`).
- RF06: `EcuSession.send_command(cmd: EcuCommand, args=None)` enfileira o comando em `_command_queue` (thread-safe). A thread de escrita drena a fila, envia o comando via transport, e registra o comando como "pendente de resposta" — publicando `EcuCommandSentEvent` no Bus.
- RF07: Quando uma linha não-frame chega na thread de leitura e há um comando pendente de resposta cujo prefixo bate com a linha, publicar `EcuCommandResponseEvent(command, raw_line)` no Bus e resolver o comando como "respondido".
- RF08: `_fetch_breakpoints()` envia `MAP_BREAKPOINTS` e `RPM_BREAKPOINTS`, aguarda as respostas, parseia e chama `vehicle_state.set_map_breakpoints()` / `vehicle_state.set_rpm_breakpoints()`.
- RF09: `_fetch_ve_map()` envia `VE_ROW_1` até `VE_ROW_16`, aguarda respostas e chama `vehicle_state.set_ve_map()` para cada linha.
- RF10: Método nomeado `open_loop()` enfileira `EcuCommand.LAMBDA_LOOP_OPEN`; `close_loop()` enfileira `EcuCommand.LAMBDA_LOOP_CLOSE`.
- RF11: Em caso de reconexão (3 leituras vazias consecutivas ou exceção), a thread de leitura fecha o transport, aguarda e tenta reconectar — repetindo o handshake completo.
- RF12: `EcuSession` implementa `is_connected() -> bool` e `get_connection_status() -> EcuConnectionStatus`.

## Requisitos Não Funcionais

- RNF01: A Session usa `threading.Thread` (não `QThread`) — publicações no EventBus são thread-safe via `pyqtSignal`.
- RNF02: Timeout de resposta: aguardar até 5 segundos por resposta de comando. Após timeout, reenviar o comando (até 3 tentativas). Após 3 falhas, logar warning e continuar.
- RNF03: `EcuSession` não deve chamar nenhum método Qt diretamente exceto via EventBus.
- RNF04: O registry `app/ecu_connection/__init__.py` deve expor `register_ecu_session()` / `get_ecu_session()` como substitutos do par `ecu_connection` / `ecu_connection_thread`.

## Especificações Técnicas

### Localização
`app/ecu_connection/session.py`

### Estrutura de threading

```
main thread
    └─ ecu_session.start()
          ├─ _read_thread = threading.Thread(target=_read_loop)  → daemon=True
          └─ _write_thread = threading.Thread(target=_write_loop) → daemon=True

_read_loop:
    open transport → handshake → streaming loop
    → classifica linha → publica no Bus ou coloca em _response_queue

_write_loop:
    aguarda _command_queue.get()
    → writeline(cmd_str)
    → publica EcuCommandSentEvent
    → coloca (cmd, expected_response_prefix) em _pending_response

_response_queue: queue.Queue   # lida por _read_loop, colocada por _read_loop ao classificar resposta
_pending_response: dict ou threading.Event  # sincronização entre _write_loop e _read_loop
```

### Mecanismo de request/response

Para cada comando enviado pelo `_write_loop`:
1. Colocar em `_pending_commands: list[(EcuCommand, expected_prefix)]` com um `threading.Event`.
2. A thread de leitura, ao receber uma linha que não é frame, itera `_pending_commands` e verifica se o prefixo bate.
3. Se bater: remove da lista, emite `EcuCommandResponseEvent`, sinaliza o `Event`.
4. `_write_loop` pode fazer `event.wait(timeout=5)` antes de enviar o próximo comando.

Para o handshake síncrono (dentro da thread de leitura):
- Usar o método `_send_and_wait(cmd, expected_prefix, timeout=5, retries=3) -> Optional[str]` internamente, que escreve no transport e lê em loop até encontrar a resposta esperada — sem a thread de escrita.
