# HIST-04: Adicionar Novos Eventos ECU ao EventBus (ECU_MESS_FRAME, ECU_COMMAND_SEND, ECU_COMMAND_RESPONSE)

## Contexto

Atualmente o EventBus tem 6 tipos de evento. A nova arquitetura de `EcuSession` exige três novos eventos para desacoplar a camada de comunicação do restante do sistema: `ECU_MESS_FRAME` (para cada frame de streaming recebido), `ECU_COMMAND_SEND` (quando um comando é enviado) e `ECU_COMMAND_RESPONSE` (quando a ECU responde a um comando). Adicionalmente, o evento `VEHICLE_STATE_CHANGED` existe no enum mas nunca é publicado no Bus — ele precisa ser conectado ao Bus para substituir o `vehicle_state.emitter` direto.

## História de Usuário

Como desenvolvedor, quero que todos os eventos de comunicação ECU e mudança de estado estejam definidos no EventBus com tipos e dataclasses apropriados, para que qualquer componente possa se inscrever sem depender de sinais Qt diretos ou acoplamento de módulo.

## Requisitos Funcionais

- RF01: Adicionar `ECU_MESS_FRAME` ao `AppEventType` com dataclass `EcuMessFrameEvent(frame_id: str, raw_line: str)`.
- RF02: Adicionar `ECU_COMMAND_SEND` ao `AppEventType` com dataclass `EcuCommandSentEvent(command: EcuCommand, args: list)`.
- RF03: Adicionar `ECU_COMMAND_RESPONSE` ao `AppEventType` com dataclass `EcuCommandResponseEvent(command: EcuCommand, raw_line: str)`.
- RF04: Adicionar os três novos `pyqtSignal(object)` em `_EventBusQObject`.
- RF05: Adicionar as três entradas em `_SIGNAL_ATTR` do `bus.py`.
- RF06: O evento `VEHICLE_STATE_CHANGED` já existe no enum e na dataclass. Verificar que `VehicleStateChangedEvent` tem campos suficientes para os três subtipos: MAP_BREAKPOINTS, RPM_BREAKPOINTS, FUEL_MAP. Se os campos `change_type: Any` e `args: tuple` forem suficientes, manter como estão. Documentar o contrato de uso.

## Requisitos Não Funcionais

- RNF01: Cada dataclass deve ser `frozen=True` e herdar de `AppEvent`.
- RNF02: Os campos de `EcuCommand` nos eventos devem ser tipados como `EcuCommand` (não `Any`), mas usar `from __future__ import annotations` para evitar importação circular se necessário.
- RNF03: `frame_id` em `EcuMessFrameEvent` deve ser uma das strings `"D01"`, `"D02"` ou `"D03"` — validar ou documentar como invariante.

## Especificações Técnicas

### Mudanças em `app/event/app_events.py`

```python
from app.masterinjection.protocol import EcuCommand  # verificar se há ciclo

class AppEventType(Enum):
    # ... existentes ...
    ECU_MESS_FRAME        = auto()
    ECU_COMMAND_SEND      = auto()
    ECU_COMMAND_RESPONSE  = auto()


@dataclass(frozen=True)
class EcuMessFrameEvent(AppEvent):
    type_: AppEventType = field(default=AppEventType.ECU_MESS_FRAME, init=False)
    frame_id: str = ""       # "D01", "D02", "D03"
    raw_line: str = ""


@dataclass(frozen=True)
class EcuCommandSentEvent(AppEvent):
    type_: AppEventType = field(default=AppEventType.ECU_COMMAND_SEND, init=False)
    command: Any = None      # EcuCommand — Any para evitar import circular
    args: tuple = field(default_factory=tuple)


@dataclass(frozen=True)
class EcuCommandResponseEvent(AppEvent):
    type_: AppEventType = field(default=AppEventType.ECU_COMMAND_RESPONSE, init=False)
    command: Any = None      # EcuCommand
    raw_line: str = ""
```

### Verificação de importação circular

`app_events.py` importa `EcuCommand` de `app/masterinjection/protocol.py`. `protocol.py` não importa nada de `app/event/`. Não há ciclo. Tipagem pode ser concreta.

### Sobre VEHICLE_STATE_CHANGED

O evento existe em `AppEventType` e em `VehicleStateChangedEvent` mas nunca é publicado no Bus. A migração de publicação para o Bus acontecerá em HIST-07 (VehicleState). Por enquanto, apenas documentar na dataclass o contrato de `change_type` e `args`:

```
change_type = EventType.MAP_BREAKPOINTS  → args = (list[int],)
change_type = EventType.RPM_BREAKPOINTS  → args = (list[int],)
change_type = EventType.FUEL_MAP         → args = (int, list[int])  # (row_idx, ve_line)
```
