# HIST-03: Refatorar EcuConnectionMock para usar EcuSession + MockTransport

## Contexto

A `EcuConnectionMock` atual ignora o protocolo de request/response: ela emite linhas raw diretamente via `self.emitter`, popula `VehicleState` diretamente (sem passar pelo Bus) e não implementa handshake. Com a nova arquitetura `EcuSession + MockTransport`, o mock deve simular o protocolo completo — sendo um `MockTransport` que responde a comandos em vez de uma `EcuConnection` separada.

## História de Usuário

Como desenvolvedor, quero que o modo mock replaye um CSV de log e simule respostas de protocolo via `MockTransport`, para que a `EcuSession` possa ser usada com o mock sem código especial de desvio.

## Requisitos Funcionais

- RF01: Criar `MockEcuTransport` (ou renomear o `MockTransport` de HIST-01) especializado para replay de CSV.
- RF02: `MockEcuTransport` deve, ao receber um `writeline()` com prefixo de comando conhecido, enfileirar a resposta correspondente em `push_read_line()`:
  - `#D50` (ECU_INFO) → responder `#D50;ECU_MOCK`
  - `#I21` (MAP_BREAKPOINTS) → responder `#I21;20;30;40;50;60;70;80;90;100;120;140;160;180;200;220;240`
  - `#I20` (RPM_BREAKPOINTS) → responder `#I20;400;800;1200;1600;2000;2400;2800;3200;3600;4000;4400;4800;5200;5600;6200;6800`
  - `#F01` a `#F16` (VE rows) → responder com a linha VE correspondente do CSV/hardcoded
  - `#D01` (STREAMING_START) → responder `#D01` para confirmar e iniciar o streaming do CSV
  - `#D05` / `#D06` (LAMBDA_LOOP) → responder com eco do comando
- RF03: Após o handshake, `readline()` deve retornar linhas do CSV de log em sequência, com timing baseado nos timestamps registrados (equivalente ao comportamento atual de `EcuConnectionMock.run()`).
- RF04: O mock deve emitir D01 e D02 como linhas separadas, NÃO como string combinada — porque `EcuSession` espera uma linha por vez.
- RF05: `EcuConnectionMock` existente deve ser removido ou marcado como deprecated e não referenciado em `main.py`.

## Requisitos Não Funcionais

- RNF01: A lógica de timing (sleep entre linhas do CSV) fica em `MockEcuTransport.readline()`, não na Session.
- RNF02: `MockEcuTransport` deve ser thread-safe (as duas threads da Session lerão e escreverão concorrentemente).

## Especificações Técnicas

### Localização

`app/ecu_connection/mock_transport.py` — novo arquivo contendo `MockEcuTransport`.

### Lógica de replay

O CSV atual tem linhas combinadas (timestamp; event; #D01;...; #D02;...) ou linhas separadas dependendo da origem. O `MockEcuTransport` deve:

1. Na inicialização: carregar o CSV e criar um iterador de linhas.
2. No `writeline()`: verificar se é um comando de handshake e responder imediatamente com `push_read_line(resposta)`.
3. No `readline()`:
   - Se há resposta de handshake pendente na fila, retorná-la imediatamente.
   - Caso contrário, avançar para a próxima linha do CSV e retorná-la (com sleep de timing).
   - Se o CSV for do formato "master" (não tem timestamp na col 0), emitir apenas as linhas `#D01` e `#D02` separadamente.
   - Se o CSV for do formato "this" (tem timestamp), parsear e fazer sleep proporcional.

### Dados VE hardcoded para mock

Usar os mesmos valores presentes em `EcuConnectionMock.run()` para as linhas `#F01` a `#F16`.

### Lógica de detecção de formato do CSV

```python
# linha de header: se tem 34 campos (timestamp; event; #D01;... colunas) → formato "this"
# caso contrário → formato "master" (linhas #D01;... separadas)
header = first_line.replace(',', ';')
if header.count(';') == 33:
    log_origin = "this"
else:
    log_origin = "master"
```

No formato "this", as linhas precisam ser separadas de volta em D01 e D02 antes de emitir (ou simplesmente emitidas como-estão se a Session souber lidar com linha combinada — mas com a nova arquitetura a Session espera D01 e D02 separados).
